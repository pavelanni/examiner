# Защита вызовов LLM (#47)

Параметры сервера задаются через CLI, переменные `EXAMINER_*` или конфигурационный
файл, с обычным приоритетом: CLI → окружение → файл → значения по умолчанию.

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `llm-timeout` | `90s` | Максимум одной попытки, включая очередь перед HTTP-вызовом |
| `llm-max-retries` | `3` | Дополнительные попытки после первой; допустимо от 0 до 100 |
| `llm-max-concurrency` | `4` | Общий предел одновременных HTTP-вызовов одного клиента/процесса |

Тайм-аут и параллельность должны быть положительными. Значения тайм-аута,
переполняющие общий временной бюджет, отклоняются. Например:

```bash
EXAMINER_LLM_TIMEOUT=45s \
EXAMINER_LLM_MAX_RETRIES=2 \
EXAMINER_LLM_MAX_CONCURRENCY=4 \
./bin/examiner --questions questions/physics_ru.json --lang ru
```

Пароль администратора и доступ к модели задаются обычным способом.

## Повторные попытки и время ожидания

Повторяются тайм-ауты и сетевые ошибки, HTTP 429 и 5xx, повреждённый JSON
HTTP-ответа или оценки, отсутствие `choices` и JSON `null` вместо оценки.
Другие HTTP-ошибки, включая 400 и 401, возвращаются сразу. Отмена родительского
контекста также не повторяется.

Задержка между попытками растёт экспоненциально: 250 мс, 500 мс, 1 с и т. д.,
до 10 с. Jitter выбирает значение между половиной и полной задержкой.
`Retry-After` в секундах или формате HTTP-date задаёт минимальную задержку,
если она больше backoff. Во время ожидания слот параллельности освобождён.

Весь вызов, включая очередь и ожидание повторов, имеет бюджет:

```text
llm-timeout × (llm-max-retries + 1) + 10s × llm-max-retries
```

При значениях по умолчанию это максимум 390 секунд. Более ранний дедлайн
родительского контекста имеет приоритет. Если `Retry-After` выходит за оставшийся
бюджет, вызов завершится по дедлайну, не отправляя преждевременный повтор.
Проверка доступности `/models` выполняется одной попыткой с `llm-timeout`.

## Параллельность и контексты

Общий семафор ограничивает все запросы к модели. Дополнительный семафор
ограничивает финальную оценку числом `max(1, llm-max-concurrency - 1)`.
При лимите больше одного это оставляет хотя бы один слот интерактивной оценке
ответов даже при очереди финальных оценок. При лимите 1 обе операции используют
единственный слот без резерва. Ожидание обоих семафоров отменяемое. Его тайм-аут отличается от тайм-аута
запроса к модели (`ErrQueueTimeout`) и не расходует повторы запросов к модели.
При нехватке слота сдача отвечает 503, сохраняя экзамен доступным для повторной
сдачи, без нулевой или итоговой оценки.

Интерактивная оценка наследует `r.Context()`: закрытие соединения отменяет
обращение к модели и повторы. Уже сохранённый ответ студента остаётся в SQLite. Если последним сообщением
треда является ответ без обратной связи, повтор с тем же текстом возобновляет
оценку без вставки нового сообщения. Изменённый текст до завершения оценки
отклоняется с 409; форма показывает сохранённый текст и кнопку повтора.
Это защита в пределах текущего обработчика, а не распределённая идемпотентность #49.
Финальная оценка использует контекст, отделённый от отмены браузером, с сохранением
значений запроса; каждый вызов клиента всё равно ограничен указанным бюджетом.

Текущий обработчик сдачи остаётся синхронным. Постоянная очередь, восстановление
после перезапуска и отказ от нулевых оценок при окончательной ошибке относятся
к #48; этот PR не подменяет реализацию очереди.

Предел действует в одном процессе и не ограничивает суммарную нагрузку нескольких
реплик. Четыре одновременных запроса — начальное консервативное значение, а не
результат измерений реальной модели. Его подбор выполняется в #58. При переходе
на LLM gateway следует согласовать единственного владельца повторов и бюджетов,
чтобы клиент и gateway не перемножали число попыток.

## Проверки и журналирование

`httptest.Server` проверяет зависший сервер, временные и постоянные ошибки,
`Retry-After`, отмену, восстановление после тайм-аута, резерв интерактивного слота
и предел параллельности при 100 смешанных вызовах. Отдельные тесты обработчиков
проверяют наследование и отделение контекстов, а тест CLI — приоритет настроек.

Каждая попытка журналирует операцию, модель, сессию и тред (для оценки), номер
попытки, длительность, результат и HTTP-статус. Для успешного HTTP-ответа сохраняется
журнал использования токенов. Задержка следующей попытки журналируется отдельно.
Метрики приложения относятся к #50.
